## 〇、 原型统一约定（所有原型都要遵守）

### 0.1 目录与独立运行

```
prototypes/<编号>_<英文名>/
  <name>.tscn        原型主场景（可直接 F6 运行）
  <name>.gd          原型逻辑
  debug_harness.tscn 调试外壳：模拟主线传入的参数、显示输出结果、可调参数面板
  README.md          玩法说明、参数表、已知问题
```

* 原型**不依赖主线玩法代码**，只用框架服务（`Assets`、`UI`、`Events`、`Pool`）。
* 参数全部放 `@export` 或配置表，方便策划在调试外壳里调。

### 0.2 小游戏接口契约

主线通过统一接口调用小游戏，开发小游戏的同学只需要实现这个接口：

| 接口 | 说明 |
| :--- | :--- |
| `start(context: Dictionary)` | 开始。`context` 由主线传入：角色加成（如判定区间倍率）、难度、持有物品、随机种子等 |
| `abort(reason: String)` | 被主线强制中断（如老师破门、被抓） |
| `signal noise(loudness: float)` | 过程中产生噪声（主线转成 AI 听觉事件） |
| `signal finished(result: Dictionary)` | 结束。`result` 至少含 `success: bool`、`score: float`（0~1 或分数）、`duration: float`，其余字段按各原型定义 |
| `pause_world: bool`（常量） | 小游戏进行时，主线世界是否继续运行。**本游戏绝大多数为 false**（世界不停，老师照样巡逻，这正是紧张感来源） |

### 0.3 每个原型的验收通用标准

1. 调试外壳里能从开始玩到结束，`finished` 输出的结果正确；
2. 至少 3 名非开发同学试玩，记录“好不好玩 / 难度是否合适”；
3. `README.md` 写清参数表与推荐值；
4. 有至少 1 个自动测试（规则判定部分）。

## 一、 M1 核心原型（详细）

### MG-01 撬门：扫帚杆 + 饮料瓶开机房门

| 项目 | 内容 |
| :--- | :--- |
| **要验证** | 第一人称物理微操是否“好玩又紧张”：有手感、能练习、失败代价明显 |
| **玩法** | 手持扫帚杆站在机房门外，把杆子从门上方防盗网格伸进去，控制角度与力度，用杆头的饮料瓶套住门内压柄并往下压，压到底门就开了 |
| **输入** | 鼠标移动 = 杆子俯仰 / 左右；滚轮或 W/S = 伸缩；左键按住 = 施压；右键 = 退出 |
| **流程** | 准备（对准气窗）→ 伸入 → 寻找把手 → 套住 → 下压 → 开门；任意阶段偏离过大 → 杆子掉落 |
| **物理** | 杆子是刚体或带约束的杠杆，网格开口是支点；手抖（随机微扰）随时间增强；套住判定 = 瓶口与把手距离 + 角度 |
| **噪声** | 摩擦声持续（小响度）；杆子掉落巨响（大响度，同楼层老师必听到） |
| **可调参数** | 手抖幅度与增长速度、支点摩擦、压柄所需力度、偏离容差、门内光线（夜晚看不清） |
| **主线传入** | `stability_mult`（信息竞赛生门锁专家）、是否夜晚 |
| **输出** | `success`、`duration`（8 秒内无失误触发成就）、`mistakes`（偏离次数） |
| **做 / 不做** | 做：单扇门、单把手、手抖、掉落；不做：多种门型、合作扶杆 |
| **验收** | 熟练玩家 6~10 秒开门；新手 3 次以内能成功；掉落时巨响明显 |

### MG-04 切屏 QTE 与戴耳机模式

| 项目 | 内容 |
| :--- | :--- |
| **要验证** | “老师在身后”时的极限反应是否刺激；戴耳机的高收益高风险是否成立 |
| **触发** | 有老师进入机房 / 走到身后视野时触发（由主线 AI 告知）；**戴耳机时完全听不到脚步，只能靠余光（屏幕反光 / 视野边缘）发现** |

| **输出** | `success`、`reaction_time` |
| **验收** | 判定区间与速度在调试外壳里可调；成功率曲线符合策划预期 |
